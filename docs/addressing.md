# IPv4 주소와 CIDR을 AWS 네트워크에 적용하기

이 문서는 IPv4 주소를 읽는 법, CIDR 접두사로 네트워크 범위를 계산하는 법, 그리고 그 표기가 이 프로젝트의 VPC·Subnet·라우팅·접근 제어에서 맡는 역할을 차례로 설명한다.

## IPv4 주소는 어떻게 구성되는가

IPv4는 네트워크에 연결된 장치를 구별하는 32비트 주소다. 사람이 읽을 때는 8비트씩 네 묶음으로 나누고 각 묶음을 10진수로 쓴다. 각 8비트 묶음을 옥텟이라 하며, 값은 0부터 255까지다.

```text
10.0.1.25

10       .0        .1        .25
00001010.00000000.00000001.00011001
```

주소 안에는 네트워크를 가리키는 부분과 그 네트워크의 장치를 가리키는 호스트 부분이 있다. 어디서 두 부분이 나뉘는지는 서브넷 마스크 또는 CIDR 접두사 길이로 정한다.

## 공인 주소와 사설 주소

공인 IPv4 주소는 인터넷에서 고유하게 사용되며 인터넷을 통해 직접 라우팅할 수 있다. 사설 주소는 내부 네트워크용이라 인터넷에서 직접 라우팅되지 않는다.

| CIDR | 주소 범위 | 전체 주소 수 |
|---|---|---:|
| `10.0.0.0/8` | `10.0.0.0` ~ `10.255.255.255` | 16,777,216 |
| `172.16.0.0/12` | `172.16.0.0` ~ `172.31.255.255` | 1,048,576 |
| `192.168.0.0/16` | `192.168.0.0` ~ `192.168.255.255` | 65,536 |

프로젝트 VPC의 `10.0.0.0/16`과 Public Subnet의 `10.0.1.0/24`는 모두 사설 `10.0.0.0/8` 범위에 속한다. 사설 주소만으로 EC2가 인터넷과 직접 통신할 수 있는 것은 아니다. Public IPv4 또는 Elastic IP와 Internet Gateway를 향한 네트워크 경로도 필요하다. 프로젝트의 전체 흐름은 [README의 아키텍처 설명](../README.md)에서 볼 수 있다.

## CIDR 접두사가 범위를 나타내는 방식

서브넷 마스크는 주소에서 네트워크 부분과 호스트 부분을 가른다. CIDR은 마스크를 `/접두사 길이`로 짧게 쓴 것이다. 접두사 길이는 32비트 중 네트워크 부분으로 쓰는 비트 수를 뜻한다. 예를 들어 `/24`는 앞 24비트가 네트워크, 나머지 8비트가 호스트 영역이다.

```text
CIDR:         10.0.1.0/24
서브넷 마스크: 255.255.255.0

네트워크 부분: 11111111.11111111.11111111.00000000
호스트 부분:                                      8비트
```

접두사 숫자가 커지면 네트워크에 고정되는 비트가 늘어나므로 범위가 작아진다. 숫자가 작을수록 포함 주소 범위는 넓어진다.

| CIDR 접두사 | 서브넷 마스크 | 전체 주소 수 | 일반적인 의미 |
|---|---|---:|---|
| `/0` | `0.0.0.0` | 4,294,967,296 | 모든 IPv4 주소 |
| `/8` | `255.0.0.0` | 16,777,216 | 매우 큰 네트워크 |
| `/16` | `255.255.0.0` | 65,536 | 이 프로젝트의 VPC 범위 |
| `/24` | `255.255.255.0` | 256 | 이 프로젝트의 Public Subnet 범위 |
| `/32` | `255.255.255.255` | 1 | 단일 IPv4 주소 |

호스트 부분의 비트 수로 전체 주소 개수를 계산한다.

```text
전체 주소 수 = 2^(32 - CIDR 접두사 길이)
```

이에 따라 `/24`에는 `2^(32 - 24) = 256`개, `/16`에는 `2^(32 - 16) = 65,536`개의 주소가 포함된다.

## 네트워크 주소와 AWS 예약 주소

일반적인 IPv4 서브넷은 호스트 비트가 모두 0인 첫 주소를 네트워크 주소로, 모두 1인 마지막 주소를 브로드캐스트 주소로 사용한다. `10.0.1.0/24`의 주소 범위는 다음과 같다.

| 구분 | 주소 |
|---|---|
| 네트워크 주소 | `10.0.1.0` |
| 주소 범위 | `10.0.1.0` ~ `10.0.1.255` |
| 브로드캐스트 주소 | `10.0.1.255` |
| 일반 네트워크의 호스트 주소 | `10.0.1.1` ~ `10.0.1.254` |

일반 `/24`에서는 양 끝 주소를 뺀 254개를 호스트에 할당할 수 있다. AWS VPC Subnet은 별도로 다섯 개 주소를 예약하므로 실제 할당 수는 다르다.

AWS는 Subnet CIDR 블록의 처음 네 주소와 마지막 한 주소를 예약한다. `10.0.1.0/24`에서는 아래 주소가 예약된다.

| 주소 | AWS에서의 용도 |
|---|---|
| `10.0.1.0` | 네트워크 주소 |
| `10.0.1.1` | VPC 라우터 |
| `10.0.1.2` | DNS 서버 |
| `10.0.1.3` | 향후 사용을 위해 예약 |
| `10.0.1.255` | 네트워크 브로드캐스트 주소(브로드캐스트는 VPC에서 지원하지 않음) |

따라서 이 `/24`에서 리소스에 배정할 수 있는 주소는 `10.0.1.4`부터 `10.0.1.254`까지 251개다.

```text
AWS Subnet에서 사용 가능한 IPv4 주소 수 = 전체 주소 수 - 5
```

## 프로젝트 주소 공간의 계층

프로젝트는 큰 VPC 범위 안에 작은 Subnet을 둔다.

```text
VPC: 10.0.0.0/16
└── Public Subnet: 10.0.1.0/24
```

VPC의 `10.0.0.0/16` 범위는 `10.0.0.0`부터 `10.0.255.255`까지다. Subnet의 `10.0.1.0/24`는 `10.0.1.0`부터 `10.0.1.255`까지이므로 VPC 범위 안에 온전히 들어간다.

| 설정 위치 | CIDR | 이 프로젝트에서의 역할 |
|---|---|---|
| VPC | `10.0.0.0/16` | 프로젝트 전체 사설 네트워크 |
| Public Subnet | `10.0.1.0/24` | EC2를 배치하는 VPC 내부 네트워크 |
| Route Table | `0.0.0.0/0` | 더 구체적인 경로가 없는 IPv4 트래픽의 목적지 범위 |
| HTTP Security Group | `0.0.0.0/0` | 모든 IPv4 주소의 HTTP 요청 허용 범위 |
| SSH Security Group | `운영자 공인 IP/32` | 운영자의 IPv4 한 주소에서 오는 SSH만 허용 |

CIDR 문자열이 같더라도 설정 위치에 따라 의미가 달라진다. Route Table의 CIDR은 트래픽을 보낼 목적지를 고르고, Security Group의 CIDR은 허용할 송신지 또는 목적지 범위를 나타낸다.

## 전체 주소와 단일 주소 표기

`0.0.0.0/0`은 네트워크 비트를 하나도 고정하지 않기 때문에 모든 IPv4 주소와 일치한다.

- Route Table의 `0.0.0.0/0 → Internet Gateway`는 더 구체적인 경로가 없는 트래픽을 인터넷으로 보낸다.
- HTTP 인바운드 규칙의 `0.0.0.0/0`은 모든 IPv4 주소에서의 연결을 허용한다.
- SSH에도 같은 범위를 허용하면 관리 포트가 인터넷 전체에 노출되므로 이 프로젝트는 그렇게 설정하지 않는다.

`/32`는 단 하나의 IPv4 주소를 표현한다. 예를 들어 운영자의 공인 IP가 `203.0.113.10`이면 `203.0.113.10/32`로 등록해 그 주소에서 오는 SSH만 허용할 수 있다. 운영자 주소가 바뀌면 기존 규칙과 맞지 않으므로 Security Group의 SSH CIDR을 새 주소로 갱신해야 한다.

## 범위 포함과 중복 방지

Subnet CIDR은 VPC 범위 안에 포함되어야 하며, 같은 VPC의 Subnet끼리는 겹칠 수 없다.

```text
VPC 10.0.0.0/16

10.0.1.0/24  → VPC에 포함됨
10.0.2.0/24  → VPC에 포함되고 기존 Subnet과 겹치지 않음
10.0.1.0/25  → VPC에는 포함되지만 10.0.1.0/24와 겹침
10.1.0.0/24  → VPC 범위를 벗어남
```

새 Subnet을 설계할 때는 필요한 리소스 수에서 AWS 예약 주소 다섯 개를 고려하고, 기존 Subnet 및 연결할 다른 네트워크와 주소가 겹치지 않는지 확인한다. VPC Peering, VPN, Transit Gateway로 외부 네트워크와 연결할 계획이라면 상대 네트워크 범위도 검토한다.

## 설계 검토 항목

- VPC CIDR이 계획한 모든 Subnet을 포함할 만큼 충분한가?
- 각 Subnet이 VPC 범위 안에 완전히 들어가는가?
- Subnet끼리 주소 범위가 중복되지 않는가?
- AWS가 예약하는 주소 다섯 개를 빼고도 필요한 리소스를 수용하는가?
- Route Table의 `0.0.0.0/0` 대상이 의도한 Internet Gateway 또는 NAT Gateway인가?
- Security Group에서 전체 공개가 필요한 포트만 `0.0.0.0/0`으로 허용했는가?
- SSH 같은 관리 포트는 신뢰할 단일 주소(`/32`)나 제한된 범위만 허용하는가?

이 프로젝트는 VPC에 `/16`, Public Subnet에 `/24`를 사용한다. HTTP는 전체 IPv4에 공개하고 SSH는 운영자 한 주소로 제한한다. 실제 배포 흐름과 확인 방법은 [프로젝트 README](../README.md), 정리 기록은 [리소스 정리 체크리스트](cleanup-checklist.md)를 참고한다.
